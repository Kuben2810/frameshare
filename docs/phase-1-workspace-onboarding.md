# Phase 1A: Workspace foundation and first-gallery onboarding

## Purpose

Turn Frameshare's current single-photographer account model into the minimum
sellable workspace model without changing the existing gallery proofing
experience or beginning billing/storage-provider work.

The outcome is a new photographer who can name a studio, optionally apply
their brand, create a first gallery, upload photos, and share it - all within
one guided flow. Existing photographers continue to see and operate their
current galleries.

## Product boundary

### In scope

- One default workspace for each existing and new photographer.
- Workspace ownership and member authorization, with `owner` as the only role
  initially enabled.
- Workspace-scoped brand name, logo, and accent colour.
- Workspace-scoped managed-storage quota and usage.
- An idempotent onboarding flow from studio name through first gallery.
- Migration of existing galleries and quota data to a default workspace.
- Product events for the activation funnel.

### Explicitly out of scope

- Stripe, subscriptions, invoices, trials, and plan enforcement.
- Inviting additional workspace members or permission-management UI.
- Google Drive, S3 bring-your-own storage, credential storage, or imports.
- Custom domains, custom email sender domains, and white-label removal.
- Reminder automation, durable jobs, and client CRM/history.
- Changing client gallery URLs or moving existing R2 objects.

## Why this slice comes first

Today, authentication, galleries, branding, and storage quota all attach
directly to `users`. That works for one photographer but cannot safely support
teams, workspace billing, or per-workspace storage later.

This slice establishes the ownership boundary once. Later product work should
extend `workspaces` instead of adding another parallel set of user-owned
settings.

## Domain model

### Existing model

`user -> galleries -> photos`

The authenticated user is simultaneously the personal identity, studio owner,
brand holder, quota holder, and gallery owner.

### Target model

`user -> workspace_members -> workspace -> galleries -> photos`

- A **user** is a human identity used for sign-in.
- A **workspace** is the photographer's studio and commercial boundary.
- A **workspace member** gives a user a role within that studio.
- A **gallery** belongs to one workspace. Its `user_id` remains as the creator
  / legacy-owner field for this migration, not as the authorization boundary.
- A **photo** continues to record its uploading user. Its workspace is derived
  through the gallery until a measured performance need justifies duplicating
  `workspace_id` on photos.

## Proposed database changes

### `workspaces`

| Column | Notes |
| --- | --- |
| `id` | UUID/text primary key, generated by the application. |
| `name` | Studio name displayed to clients. |
| `slug` | Reserved unique workspace identifier; do not expose as a public URL in this slice. |
| `logo_key` | Private R2 object key for the workspace logo. |
| `accent_color` | Workspace client-gallery accent colour. |
| `storage_provider` | `managed` only in this slice; establishes the later provider seam. |
| `storage_used_bytes` | Canonical workspace quota usage. |
| `onboarding_completed_at` | `null` until the first gallery has been created. |
| `created_at`, `updated_at` | Audit fields. |

### `workspace_members`

| Column | Notes |
| --- | --- |
| `workspace_id` | Foreign key to `workspaces`, cascade on workspace deletion. |
| `user_id` | Foreign key to `users`, cascade on user deletion. |
| `role` | Enum-like text: `owner`, `editor`, `viewer`. Only `owner` is granted or used in this slice. |
| `created_at` | Audit field. |

The primary key is `(workspace_id, user_id)`. Add an index on
`(user_id, workspace_id)` for active-workspace lookup.

### Existing table migration

- Add nullable `workspace_id` to `galleries` first.
- For every existing user, insert exactly one workspace and one owner
  membership. The migration must be repeatable/idempotent when practical.
- Backfill each gallery's `workspace_id` from its legacy `user_id`.
- Verify there are no galleries with a null workspace, then make
  `galleries.workspace_id` non-null and index it.
- Preserve `galleries.user_id`; redefine it in code as `created_by_user_id`
  only after a later, separately reviewed migration. Do not rename it now.
- Keep `users.logo_key`, `users.accent_color`, and `users.storage_used_bytes`
  during the transition. Copy their values to each default workspace.
- Switch reads/writes to workspace fields. Remove or deprecate user-level
  duplicates only after production data verification and a rollback window.
- Do not move existing storage keys. Existing keys are still valid because
  gallery authorization is database-driven, not key-prefix-driven.

### Data invariants

1. Every gallery has exactly one workspace.
2. Every workspace has at least one owner.
3. A user may access a workspace only through `workspace_members`.
4. A gallery mutation requires membership in that gallery's workspace.
5. Quota reservation and reconciliation use the workspace, not the user.
6. Public gallery access continues to use gallery-level policy and must never
   reveal workspace membership or storage credentials.

## Authorization seam

Introduce a small workspace access module before changing routes:

```ts
requireActiveWorkspace(userId): Promise<WorkspaceMembership>
requireWorkspaceRole(workspaceId, userId, minimumRole): Promise<WorkspaceMembership>
requireGalleryWorkspaceAccess(galleryId, userId): Promise<GalleryWithWorkspace>
```

For this first slice, active workspace selection is deterministic: the sole
workspace membership for a user. Do not put a workspace ID into the session or
build a workspace switcher until a user can belong to more than one workspace.

All existing direct `gallery.user_id = session.user.id` authorization checks
must be replaced methodically. Avoid partial migration: a route using the old
check could lock out valid future members, while a route that skips both checks
could leak another workspace's data.

## Onboarding flow

### Entry conditions

- A newly registered credentials user is sent to `/onboarding` after sign-in.
- A first-time OAuth user is provisioned idempotently on their first protected
  request and sent to `/onboarding`.
- An existing user with a migrated workspace and at least one gallery goes to
  `/dashboard`, not onboarding.
- A user with a workspace but no completed onboarding is redirected to the
  next incomplete onboarding step from protected dashboard routes.

### Screens

1. **Welcome / studio name**
   - Explain the outcome: create a first client gallery.
   - Collect a studio name; default to the photographer's account name.
   - Save workspace name and advance.

2. **Brand (optional)**
   - Logo upload and accent colour.
   - Explicit "Skip for now" action.
   - Copy should show where the brand will appear: client gallery headers and
     proofing notifications.

3. **First gallery**
   - Gallery name, optional client name, and template choice.
   - Start with a simple Proofing template; do not make template schema work a
     dependency of this slice.
   - Creates the gallery in the active workspace and redirects to its editor.

4. **Upload and share**
   - Reuse the existing editor/upload workflow.
   - Surface a contextual completion checklist: upload, preview client link,
     copy share link.
   - Mark `onboarding_completed_at` when a gallery is created, not when a
     client visits. This avoids trapping the photographer in onboarding.

The flow must be resumable. Reopening `/onboarding` should read current state
and route the user forward, never create duplicate workspaces or galleries.

## UI changes outside onboarding

- The dashboard header displays the active workspace name rather than the
  account name.
- Settings becomes **Studio settings** backed by the workspace.
- The storage card reads the workspace quota.
- The user menu remains identity-oriented (profile and sign out); no workspace
  switcher yet.
- Existing galleries retain their URLs and client branding after migration.

## Funnel instrumentation

Use a provider-neutral `trackProductEvent` seam. Do not commit to an analytics
vendor in this slice.

Events:

- `workspace_created`
- `onboarding_step_completed` with `step`
- `first_gallery_created`
- `first_gallery_shared`
- `client_gallery_opened`
- `client_selection_submitted`

Only attach actor/workspace IDs and non-sensitive metadata. Do not send client
IP addresses, gallery passwords, storage credentials, raw photo names, or
email body contents.

## Acceptance criteria

### Migration and compatibility

- A production-like database with existing users and galleries migrates
  without losing galleries, photos, selections, branding, or storage totals.
- Each existing user receives one owner workspace; all existing galleries
  point to it.
- Existing public gallery URLs and protected download behavior continue to
  work unchanged.
- Migration can be verified with counts before and after deployment.

### Authorization

- An owner can list, edit, upload to, and delete only galleries in their
  workspace.
- A user without membership receives the existing not-found/unauthorized
  behavior for gallery and upload routes.
- Public gallery viewers cannot infer workspace details.
- Tests exercise each migrated server action and API route with an unrelated
  user/workspace.

### Onboarding

- A fresh credentials and OAuth account each receive exactly one workspace.
- A new photographer can complete the guided flow, create a gallery, upload a
  photo, and copy the client link without visiting settings first.
- Skipping brand setup does not block gallery creation.
- Reloading or abandoning any onboarding step resumes safely with no duplicate
  workspace or gallery.
- Existing users are not redirected into onboarding merely because their
  historical workspace lacks a newly introduced optional field.

### Operational safety

- No production migration or deployment runs without user confirmation.
- `npm run db:generate`, targeted authorization tests, TypeScript, and a
  Vercel-mode production build pass before release.
- A documented backfill verification query is run against a Neon development
  branch before production migration.

## Implementation sequence

1. Add schema and a backward-compatible Drizzle migration; test it on the
   existing Neon `development` branch only.
2. Add workspace lookup/authorization helpers and migrate server routes in
   small, tested groups.
3. Move branding/quota reads and writes to workspaces while retaining legacy
   user fields as a rollback-compatible copy.
4. Add idempotent workspace provisioning and the onboarding route/state.
5. Rework the dashboard and studio settings to use the active workspace.
6. Add analytics seam/events and onboarding-specific tests.
7. Run a full migration rehearsal, request production migration approval, then
   deploy and smoke-test the first-gallery flow.

## Decisions deliberately deferred

- Exact pricing, storage limits, and plan entitlements.
- Whether a workspace can have multiple owners.
- Client-name/contact data model.
- Custom public gallery hostnames and workspace slugs.
- Persistent active-workspace selection for multi-workspace users.
- Storage provider credential encryption and Google Drive OAuth scopes.

## Estimated shape

This is one focused Phase 1A project, not the entire product roadmap. It
touches schema, authorization, onboarding, settings, dashboard reads, and
tests. Start it only after reviewing this specification and breaking it into
small commits; do not combine it with Stripe or bring-your-own storage.
